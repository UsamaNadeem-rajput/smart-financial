                        1. PROJECT OVERVIEW & IDEA
================================================================================

WHAT IS SMART FINANCIAL?
------------------------
Smart Financial is a full-stack, web-based Double-Entry Accounting System 
designed specifically for small to medium businesses. It provides professional
accounting capabilities without the complexity of enterprise software.

CORE CONCEPT:
The application follows the fundamental accounting equation:
    
    ASSETS = LIABILITIES + EQUITY

All transactions use double-entry bookkeeping where:
    TOTAL DEBITS = TOTAL CREDITS (always balanced)

KEY OBJECTIVES:
--------------
1. Multi-Business Support: One user can manage multiple businesses
2. Chart of Accounts: Organized ledger system with account types
3. Double-Entry Transactions: Professional accounting with validation
4. Financial Reports: Income Statement, Balance Sheet, Trial Balance, etc.
5. Cloud-Based: Access from anywhere with secure authentication
6. PDF Export: Professional reports with company branding

TARGET USERS:
-------------
- Small business owners
- Freelancers and consultants
- Startups
- Partnership firms
- Sole proprietorships
- Students learning accounting

================================================================================
                     5. AUTHENTICATION SYSTEM (DETAILED)
================================================================================

REGISTRATION FLOW (SignupForm.jsx → register.js):
-------------------------------------------------
1. User fills form: username, fullname, email, password
2. Frontend validates: all fields required, password >= 6 chars
3. POST /api/register with form data
4. Backend checks:
   - Email not already registered
   - Username not already taken
5. Password hashed with bcrypt (10 salt rounds)
6. 6-digit verification code generated
7. User inserted into database (is_verified = 0)
8. Email sent via Nodemailer (OrangeHost SMTP):
   - From: support@khushifinances.com
   - Subject: "Verify your account"
   - Body: Verification code
9. Session created with username
10. User redirected to /verify

VERIFICATION FLOW (VerifyPage.jsx → verify.js):
-----------------------------------------------
1. User enters 6-digit code from email
2. POST /api/verify with code
3. Backend compares code with stored verification_code
4. If match: is_verified = 1
5. User can now login

LOGIN FLOW (LoginForm.jsx → login.js):
--------------------------------------
1. User enters email and password
2. POST /api/login with credentials
3. Backend queries user by email
4. bcrypt.compare() verifies password
5. If match:
   - Session created: req.session.username, req.session.userId
   - Session stored in MySQL (express-mysql-session)
   - Cookie sent: connect.sid (httpOnly, secure, sameSite: none)
6. User redirected to /list (dashboard)

SESSION CHECK (PrivateRoute.jsx → login.js):
--------------------------------------------
1. Every protected route calls GET /api/login/session
2. Backend checks req.session.username or req.user (OAuth)
3. Returns username if authenticated
4. Else returns 401, redirect to /login

GOOGLE OAUTH FLOW (googleAuth.js):
----------------------------------
1. User clicks "Continue with Google"
2. Redirect to: /api/auth/google
3. Passport.js redirects to Google consent screen
4. User grants permission
5. Google redirects to: /api/auth/google/callback
6. Backend receives profile:
   - Checks if email exists in database
   - If new: creates user (is_verified = 1, no password_hash)
   - If exists: loads user
7. Session created with user data
8. Redirect to frontend: https://khushifinances.com/list

LOGOUT FLOW (auth.js):
----------------------
1. GET /api/auth/logout
2. req.logout() clears Passport session
3. req.session.destroy() removes session from MySQL
4. res.clearCookie('connect.sid') removes cookie
5. User redirected to /login

PASSWORD RESET FLOW (ForgotPassword.jsx → authReset.js):
--------------------------------------------------------
1. User enters email
2. POST /api/auth/forgot-password
3. Backend generates reset token
4. Email sent with reset link
5. User clicks link, enters new password
6. Password hashed and updated

================================================================================
                   8. TRANSACTION MANAGEMENT MODULE (DOUBLE-ENTRY)
================================================================================

DOUBLE-ENTRY BOOKKEEPING CONCEPT:
---------------------------------
Every transaction affects at least TWO accounts:
- One or more accounts are DEBITED
- One or more accounts are CREDITED
- TOTAL DEBITS must EQUAL TOTAL CREDITS

Example: Cash Sale of Rs. 10,000
   Dr. Cash Account        10,000
   Cr. Sales Revenue       10,000

TRANSACTION FORM (TransactionForm.jsx):
---------------------------------------
HEADER SECTION:
- Date: Defaults to current date, user can change
- Time: Display only (current time)
- Transaction ID: Auto-generated, sequential per business

TABLE SECTION:
- Ledger Name: Searchable input with auto-complete
- Debit: Amount (mutually exclusive with Credit)
- Credit: Amount (mutually exclusive with Debit)
- Remove: Delete row button

FEATURES:
- Minimum 2 rows (one debit, one credit)
- Auto-add new row when Enter pressed
- Running totals displayed
- Submit disabled until Debit Total = Credit Total
- Number formatting with commas (1,000,000)
- Success popup with animation and sound

BACKEND PROCESS (POST /api/transactions → transactionApi.js):
-------------------------------------------------------------
1. Validate: business_id, debit, credit, date, entries (min 2)
2. Validate: parseFloat(debit) === parseFloat(credit)
3. Begin MySQL transaction
4. INSERT INTO transactions (frontend_id, business_id, debit, credit, date)
5. For each entry: INSERT INTO transaction_entries (transaction_id, account_id, amount, type)
6. Call updateAccountBalances(conn, business_id)
7. Commit transaction
8. Return success with transaction_id

BALANCE CALCULATION LOGIC (updateAccountBalances function):
-----------------------------------------------------------
For each account in the business:

If account is ASSETS or EXPENSES (type_id: 2,3,4,5,11,13,14):
    Balance = SUM(all debits) - SUM(all credits)

If account is INCOME, LIABILITY, EQUITY (type_id: 1,6,7,8,9,12):
    Balance = SUM(all credits) - SUM(all debits)

UPDATE accounts SET balance = calculated_balance

VIEWING TRANSACTIONS (ShowTransactions.jsx → showtransactions.js):
------------------------------------------------------------------
1. User selects date range (from date, to date)
2. GET /api/showtransactions?from=YYYY-MM-DD&to=YYYY-MM-DD&business_id=123
3. Query: SELECT transactions WHERE date BETWEEN from AND to
4. Query: SELECT transaction_entries for those transactions
5. Group entries by transaction, calculate totals
6. Display with Print and Save as PDF options

EDITING TRANSACTIONS (TransactionEdit.jsx → edittransaction.js):
----------------------------------------------------------------
1. Navigate to /transaction-edit/:transactionId
2. Load existing transaction data
3. Same form as TransactionForm but pre-populated
4. PUT /api/edit-transaction/:id
5. Delete old entries, insert new entries
6. Recalculate balances

                    12. STATE MANAGEMENT (CONTEXT API)
================================================================================

BUSINESS CONTEXT (context/BusinessContext.jsx):
-----------------------------------------------

STATE:
- selectedBusiness: Currently selected business object
- businesses: Array of all user's businesses

METHODS:
- selectBusiness(business): Set selected business, save to localStorage
- clearBusiness(): Clear selection on logout
- setBusinesses(arr): Update businesses list after fetch

PERSISTENCE:
- localStorage.setItem('selectedBusiness', JSON.stringify(business))
- On app load, check localStorage and restore selection

USAGE:
- Import: import { useBusiness } from '../../context/BusinessContext'
- Access: const { selectedBusiness, selectBusiness } = useBusiness()

FLOW:
1. User logs in → navigates to /list
2. List.jsx fetches businesses from API
3. User clicks business card
4. selectBusiness(business) called
5. All components access selectedBusiness.business_id
6. On logout: clearBusiness() removes from Context and localStorage

================================================================================
                         14. SECURITY FEATURES
================================================================================

PASSWORD SECURITY:
------------------
- Bcrypt hashing with 10 salt rounds
- Minimum 6 character requirement
- Never stored in plain text

SESSION SECURITY:
-----------------
- httpOnly cookies (not accessible via JavaScript)
- secure: true (HTTPS only)
- sameSite: 'none' (for cross-origin API)
- Session stored in MySQL (not in memory)
- 24-hour session expiry

API SECURITY:
-------------
- CORS configured for specific origins only
- All protected routes check req.session.username
- 401 Unauthorized returned for unauthenticated requests
- Input validation on all endpoints

FILE UPLOAD SECURITY:
---------------------
- Multer file type restriction (jpeg, jpg, png, gif only)
- 2MB file size limit
- Random filename generation (prevents overwrite attacks)
- Files served with CORS headers

SOFT DELETE:
------------
- Businesses not permanently deleted
- is_deleted flag preserves data
- Prevents accidental data loss

                        16. DATA FLOW DIAGRAMS
================================================================================

USER REGISTRATION FLOW:
-----------------------
User → SignupForm → POST /api/register → Validate
                                            ↓
                                      Hash Password
                                            ↓
                                      Generate Code
                                            ↓
                                      INSERT users
                                            ↓
                                      Send Email
                                            ↓
                        ← 201 Created ← Create Session
                                            ↓
                                      Redirect /verify

TRANSACTION CREATION FLOW:
--------------------------
User → TransactionForm → POST /api/transactions
                                    ↓
                              BEGIN TRANSACTION
                                    ↓
                              INSERT transactions
                                    ↓
                              INSERT transaction_entries (loop)
                                    ↓
                              updateAccountBalances()
                                    ↓
                              COMMIT TRANSACTION
                                    ↓
                   ← 200 OK ← Response with transaction_id

REPORT GENERATION FLOW:
-----------------------
User → BalanceSheet → GET /api/balance-sheet?date=2026-01-17&business_id=5
                                    ↓
                              Query accounts with types
                                    ↓
                              Query transaction_entries before date
                                    ↓
                              Calculate balances by type
                                    ↓
                              Group by category (Asset/Liability/Equity)
                                    ↓
                   ← JSON Response ← Return structured data
                                    ↓
                              Render HTML table
                                    ↓
                              PDF/Print export available
